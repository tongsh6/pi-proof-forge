# 系统能力审计与重构台账（应用机制摘要）

历史审计日期：2026-11-09。本文保留应用架构、生成和投递链路的机制发现；个人材料、职业档案、候选岗位、简历内容和投递结果留在本地记录中。这里的历史定位用于解释改动原因，不代表所有问题仍存在于当前实现。

## 一、能力评级与验证方式

评级区分：有行为证据的可用能力、已接通但有缺口、只有实现尚未验证、以及机制与契约矛盾。文件存在、测试数量和运行退出码都不能替代用户可观察结果。

| 能力 | 归属 | 核对重点 |
| --- | --- | --- |
| 证据提炼 | evidence engine、来源与复审 | 完整命题、具体来源、来源修订与人工采纳边界 |
| 语义匹配 | matching engine | 判断与取证分离、逐项引用、失败及未评范围 |
| 定向生成 | generation engine | 事实级选材、实际正文、独立 trace、责任与条件保留 |
| 四层质量 | evaluation tiers | 评估同一实际正文和现行证据；分析建议不授予发送权限 |
| PDF 导出 | 共享 HTML/CSS 与 exporter | 与预览一致、页数及裁切、失败不伪造导出成功 |
| 运行记录 | orchestration 与持久化适配器 | 单一归属、原子写入、幂等和恢复 |
| 投递与反馈 | 既有审批、发送与回执 | 目标/版本绑定、未知不重试、来源可回溯 |

## 二、架构缺陷与修复归属

| 历史缺陷 | 根因 | 处理边界 |
| --- | --- | --- |
| CI 未覆盖完整 Python 回归与工程门禁 | 发布证据与本地工作脱节 | 在既有 CI 接入测试和 arch/roadmap/AIEF 检查 |
| sidecar facade 反向依赖与循环导入 | 业务职责没有落在唯一归属层 | 沿现有 handler/service 拆清依赖，不增加平行入口 |
| 无消费者的领域定义、重复资格判定 | 对象存在被误当作复用理由 | 查调用和消费者，移除空壳并合并真正同责规则 |
| 多套 run record 路径和非原子写 | 持久化协议分散 | 复用运行记录和原子 IO，不另建台账 |
| 错误由零散字符串解释 | 状态与失败语义没有跨层契约 | 在既有错误边界明确原因与可行动状态 |

## 三、生成机制的历史缺陷

- 卡级 top-N 和硬截断发生在事实级相关性分析前，导致更相关事实没有进入选材机会。
- 时间字段缺失曾造成整卡退出正文，应区分需要补证的事实与独立可用的事实。
- 行动/结果按索引配对、配对失败即丢弃，会损失独立事实，也可能暗示未经证明的因果关系。
- 职业概述的机械条数截断、跨阶段重新排序，会覆盖目标版本的内容取舍。
- 版式密度不能反向增强或删减事实限定；PDF 页数与正文质量须分别验收。
- 生成、追溯和量化必须消费同一条实际采用的结果证据，不能从整卡或未采用的兄弟事实加分。

当前设计以 [简历质量与证据推断](../../openspec/changes/resume-quality-standard-and-evidence-inference/design.md) 为准。

## 四、投递链路的历史缺陷

附件、字节身份、审批与回执若分散维护，恢复流程容易把“已上传”“已绑定”“已发送”混为同一状态。应沿已有身份与阶段核验，保留失败/未知结果，不能通过重试、自动改路或事后补写证据制造成功。质量分析与偏好匹配属于建议层；来源真实性、具体授权和不可逆外部副作用继续受硬边界约束。
