# Spec: evidence-provenance

## 目的

在不违反 No Fabrication 的前提下，让证据卡的 `time_range` 与 `role_scope` 能由**带出处的推断**补齐，而不是只认原文逐字或推给用户手填。推断与编造的区别：推断有可回读的依据、有置信度、可被用户一键否决、在简历措辞上降级。

## R1 可信等级

| 等级 | 名称 | 定义 | 依据示例 |
| --- | --- | --- | --- |
| L1 | 原文明示 | 所选文档中有直接陈述 | "2023 年 Q3 我负责统一运动中心改造" |
| L2 | 元数据推断 | 来自文档路径/文件名日期、文档内日期标题、修改时间，或职业档案任职区间约束 | `worklog/2023-08-15.md` 提到该项目；任职区间 2022.6–2024.3 |
| L3 | 跨文档推断 | 多份文档的共现、首尾出现时间、第一人称句频次等综合推理 | 周报 2023-03 至 2023-09 连续出现该项目，之后消失；7/9 条为"我推动/我决策" |
| L4 | 本人陈述 | 用户在 App 中口述/填写，系统记录为 self-reported | 对账面板中用户填写"2023.3–2023.9，负责人" |
| L5 | 无依据 | 以上均无 | 字段留空 |

- 等级随字段存储，不随卡整体存储：同一张卡的 `time_range` 可为 L2、`role_scope` 可为 L4。
- 用户确认一条 L2/L3 候选后，字段等级保持 L2/L3（标记 `confirmed_by_user`），不升为 L1；用户手改为不同值则记为 L4。

## R2 字段

证据卡新增（YAML，向后兼容，缺省视为 L1 或 L5）：

```yaml
time_range: "2023-03 ~ 2023-09"
time_range_provenance:
  level: L3
  precision: month          # year | month | day
  evidence:
    - {material_id: mat_xxx, document_id: doc_yyy, sha256: ..., excerpt: "..."}
  confidence: 0.72
  confirmed_by_user: true
  confirmed_at: 2026-10-18T10:00:00+08:00
role_scope: "平台负责人"
role_scope_provenance:
  level: L3
  evidence: [...]
  first_person_hits: {owner: 7, participant: 2}
  confidence: 0.65
  confirmed_by_user: true
```

- 卡 sha256 指纹计算包含 provenance 字段；卡内容变化即推断失效，沿用 `evidence_triage` 的绑定方式。
- 任职区间约束来自已确认职业档案；候选时间落在任职区间外时不得提名，改为"冲突"提示。

## R3 职责归因与简历表达

| 字段 | L1 / L4 | L2 | L3 | L5 |
| --- | --- | --- | --- | --- |
| 时间 | 按原精度 | 按推断精度（年或年月） | 年精度，且摘要不写具体月 | 不进正文 |
| 角色 | 按事实职责表达 | — （时间字段无角色含义） | 保留已采纳的职责与限定，不因 L3 自动降为参与 | 不写角色，只写动作与结果 |

- 2026-10-20 用户明确的产品取向：归属于用户经历的项目，缺少细分职责记录且没有反向材料时，候选分析优先采用主导/负责人视角；明确的参与、协助或他人负责记录仍按事实限定。默认归因属于 L3 待确认推断，不冒充 L1 原文明示，也不扩成独立完成或全权负责所有成果。
- 生成器不按 L3 等级机械替换“主导/负责人”；已采纳职责、行动与责任限定保持原义，trace 保留实际呈现文本及 provenance。LLM 改写不能超出已采纳职责范围。用户确认、卡片审核与投递授权继续由各自既有入口完成。
- R1.4 对带出处且已由用户确认的 L3 职责不因等级自动拒绝“负责/主导”；未确认的默认归因仍是候选，不能自动当成已证实责任。带引用的语义判项继续核对表述是否超出职责范围。
- 突出点（`resume-quality` R4.3）只接受 L1/L2 时间与 L1/L4 角色。

## R4 推断候选的产生

- R4.1 单文档提炼（`evidence.generateDraft`）提示词注入：文档路径、文件名、文档内首个日期标题、修改时间、所选公司的任职区间。要求模型按 L1/L2 分别给出 `time_range` 与依据，而不是一律留空。
  - 职责的原文明示可以来自人物/角色章节及明确主体，不强制逐句出现“我”；只有跨文档关联才能确定的归属留给 L3 候选，不能将用户收录材料本身当作独立负责的证明。
- R4.2 跨文档推断（新 RPC `evidence.inferFields`）：对缺时间/缺角色且分流为"值得补"的卡，使用 `kb` 索引按标题/标签/技术栈检索相关文档，汇总年月线索与第一人称句，由 LLM 产出 L3 候选（含引用 + 置信度）。单卡一次调用；结果缓存按卡指纹与文档集合指纹。
  - 检索优先保留卡已绑定且 material_id/document_id/sha256 一致的来源，再按卡标题相关性排序；长背景描述、通用技术栈与材料包标签不能挤掉直接来源和同主题文档。设计资料与合成夹具的排除规则仍生效。第一人称参与线索须包含“我/本人参与、协同、配合、支持”等主体，系统能力或数据“参与计算”不计为本人职责。排序或线索规则变化后旧推断缓存失效，既有否决记录保留。
  - 模型输入须保留有界原文语境，不以第一人称规则命中作为阅读门槛：每篇提供至多 1000 字符的原文开头、截断标记与原有关键句；优先纳入绑定材料中的职业汇总，并提供与该卡关联的已确认任职职责上下文。明确第一人称计数只是辅助信号；上下文不足时说明不足，不虚构原文。任职上下文和公共指令纳入缓存指纹。
- R4.3 候选不写卡。进入对账面板"待确认"区，用户可：接受 / 修改后接受（转 L4）/ 否决（记录否决，不再重复提名同一候选）。
  - 同一卡的字段连续确认时，客户端使用前一次成功返回的新卡指纹；后端保留未修改字段的 provenance。部分成功后按实际结果更新剩余候选和计数，失败不重复接受已完成项，也不自动重跑模型。接受仍进入待审核，不等于简历或投递批准。
- R4.4 置信度低于阈值（默认 0.5）的候选仍展示但折叠，默认不选中。

## R5 边界

- 推断只针对 `time_range` 与 `role_scope`；`results` / `artifacts` 继续要求原文逐字，缺失仍阻断进入候选池。
- 不以 JD 要求、岗位画像或其他候选人的材料作为推断依据。
- 推断调用计入 LLM 用量并可在系统设置关闭；关闭时对账面板只显示规则可得的 L2 线索。

## 验收口径

- 真实 85 卡上运行推断后，由用户在真实 App 批量确认；以确认后的缺时间/缺角色计数为准。
- 任一被用户否决的候选在后续运行中不得以相同依据再次提名。
- 任一进入简历正文的 L2/L3 字段在 `resume_trace` 中显示等级、依据与确认记录。
