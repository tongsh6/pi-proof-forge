# Spec: resume-quality

## 定位

简历（Resume）是面向**目标岗位的招聘决策者**（HR 初筛 + 用人经理）的 1–2 页**事实型说服文档**。它不是经历清单、不是项目档案、不是泛用文档。质量以读者行为定义：

- 首屏（第一页上半）30 秒内让读者得出"值得面试"的判断；
- 细读时每一句都能在面试中被追问并经得起追问；
- 内容为**这一个目标 JD** 组织，而非一份简历投所有岗位。

所有判据必须在这一定位下解释。与定位无关的"文档质量"（如字数、格式美观）只作为合格层的硬约束，不计入优质/突出。

## 四层标准

```
 突出 (Distinct)   ── 相对目标 JD 的差异化证据，置于首屏
 优质 (Strong)     ── 每条 bullet 场景-动作-结果，量化、无空话、不重复
 对位 (Fit)        ── JD 职责/要求 ↔ 正文支撑矩阵，首屏对准 JD 前三条
 合格 (Eligible)   ── 硬门禁：不编造、可追溯、与档案一致、篇幅、无内部痕迹
```

下层不通过时上层不评；质量报告仍列出上层发现，供修复参考。

### R1 合格（硬门禁，全部必须通过）

- R1.1 正文每条事实可追溯到证据卡或已确认职业档案（沿用既有 `resume_trace` 独立追溯）。
- R1.2 正文中出现的公司、职位、任职区间与已确认职业档案一致；项目时间落在对应任职区间内。
- R1.3 正文中每条经历/项目都有时间（至少到年）；无时间的证据卡不得进入正文。
- R1.4 角色措辞不超出已采纳职责范围（见 `evidence-provenance` R3）；有出处且已由用户确认的 L3 主导/负责人职责不因等级自动失败，未确认的默认归因仍不可当成已证实责任。
  已完整追溯且逐字保留已确认职业档案原句的职责，可直接核对通过；新增或改写的职责、无完整追溯或未确认档案仍需语义判项，不用模型漏项否定用户已确认的原句。
- R1.5 篇幅：PDF 1–2 页，无裁切；首屏包含定位摘要与至少一条核心经历。
- R1.6 候选人可见 PDF 不含 Evidence trace、本机路径、内部 id、系统版本标题。
- R1.7 不违背 JD 硬性条件（年限、学历、必需资质）——违背时标记而非隐瞒，由用户决定是否投递。
- R1.8 结构为简历结构：头部（姓名/联系方式/定位）→ 摘要 → 经历（按相关度与时间）→ 项目/成果 → 技能 → 教育；章节缺失须有理由（如用户选择不展示教育）。

### R2 对位（符合目标 JD）

- R2.1 JD 职责与要求逐条映射到正文 bullet，状态为 `supported / weak / absent`；输入复用既有语义评审（11 项任职要求、8 项职责、85 子项的 `all_requirements_supported` 结构），本层只增加"是否在正文呈现"与"呈现位置"。
- R2.2 JD 前三条职责（按 JD 顺序或用户标注权重）在首屏均有 `supported` 的 bullet。
- R2.3 must-have 关键词在正文语义覆盖（沿用 `llm_semantic_coverage`），不再把规则 `coverage` 作为主指标。
- R2.4 与 JD 无关的经历被压缩或退出正文（判据：无任何 JD 条目映射到它，且不是时间线必需）。
- R2.5 `absent` 项必须转为缺口任务并出现在审批页，而不是在正文用泛化语句掩盖。

粗筛相关度不是整岗合格门槛。已确认归属且字段完整的证据仍进入逐项能力评审；被逐项原文引用正向支持的项目，不因粗筛零分永久退出选材。保留粗筛原记录和逐项依据，不自动提升该卡无证据支持的要求。列举专业、技术或工具后以“等”收束的示例保留整体语境，不拆成全部同时必须具备。

逐卡粗筛缓存绑定完整请求、目标岗位及本批卡和其来源指纹；只改职业档案或其他批次卡，不应重算本批粗筛。逐项评审仍绑定完整评审输入及档案指纹，引用原文和本次所有输入在读缓存后继续校验，不能用减少调用替代证据校验。

判项输入须包含实际正文的摘要、经历上下文、技能与教育，保留可定位的 bullet/行号；不得因输入遗漏而判定缺失。正向支撑必须指向正文中存在的位置，证据池有内容但正文未呈现不能算作正文覆盖。`absent` 可引用本次完整正文审阅范围并说明缺口，不强迫引用无关成果。R2.4 按条目内的正文引用映射判断，不要求项目名出现在 JD 中。缺项/无效引用只允许一次有界纠错，仍不完整时显式待判，不缓存为完整结果；缓存绑定实际 JD、判项输入和提示词。

### R3 优质（表达）

- R3.1 每条经历 bullet 具备 场景（规模/约束）- 动作（本人做了什么）- 结果（可验证）三段；允许合并成一句，但三段缺一则标记。
- R3.2 首屏 bullet 中含可验证量化结果的比例 ≥ 60%；全文 ≥ 40%。量化指"有数字且数字来自证据卡 results"，不是正文数字字符计数。
- R3.3 空话词表（如"深入理解""丰富经验""积极推动"等，可配置）在正文出现 0 次。
- R3.4 同一成果在全文只出现一次；跨项目重复的场景/成果保留一处并保留 trace。
- R3.5 定位摘要 ≤ 3 行，明确"做什么 + 在什么规模/领域 + 对目标岗位的匹配点"，不含通用形容词。
- R3.6 动词、时态、数字格式、术语大小写一致。

R3.1 的场景可来自同一经历的标题和场景正文；结果包括已完成、可验证的非数值交付，不能将 R3.2 的量化要求重复施加于每条结果。目标简历优先展示核心项目，技能与补充成果不得将核心项目推到第二页；优先保留前三职责对应行动与可验证的指标改善。独立的行动/成果列表不能按索引配对，同项目或同 JD 条目也不能单独证明因果关联；保持原文与独立 trace。

已由 trace 完整核验且实际呈现的 `results` 原文可直接确认结果段；场景与行动仍分别判定，量化比例不因此放宽。突出点模型提名允许多于两个候选，经既有排序选出最多两个展示；候选数量不能当作已经选中的数量处罚。

### R4 突出（相对目标 JD 的差异化）

- R4.1 突出点定义：满足 JD 某条职责/要求，且**规模、难度、范围或稀缺组合**明显超出 JD 字面要求的证据；或 JD 未明说但该岗位簇公认加分的能力（由 JD 解析中的 `level_signals` / 业务域推断）。突出点**只相对目标 JD 定义**，换 JD 必须重算。
- R4.2 每份简历至少 1 条、最多 2 条突出点，置于首屏（摘要或第一条经历）。
- R4.3 突出点证据可信等级必须为 L1 或 L2；L3/L4 可作为普通 bullet，不可作为突出点。
- R4.4 系统提名突出点并给出理由（对应 JD 条目 + 超出之处 + 证据引用）；用户可替换或否决，否决后重新提名。
- R4.5 无合格突出点时不编造，质量报告标记"无突出点"并给出最接近候选与补证据任务。

## 质量报告（替代单一分数）

```yaml
quality_report:
  resume_version: <sha256>
  job_profile_id: <id>
  tiers:
    eligible: {passed: bool, failures: [{rule: R1.3, target: "bullet#4 / ec_xxx", reason: "..."}]}
    fit:      {passed: bool, matrix: [{jd_item, status, bullet_ref, first_screen: bool}], failures: [...]}
    strong:   {passed: bool, metrics: {quant_first_screen: 0.67, quant_total: 0.45, filler_hits: 0}, failures: [...]}
    distinct: {passed: bool, highlights: [{bullet_ref, jd_item, exceeds: "...", provenance: L1}], failures: [...]}
  auto_pass: bool
  gap_tasks: [...]
  legacy_scores: {rule_total, llm_expression}   # 仅供对比，不参与 auto_pass
```

- `auto_pass = eligible.passed ∧ fit.passed ∧ strong.passed ∧ distinct.passed`。
- 每条 failure 指向具体 bullet 或证据卡，不得只给总体评语。
- 旧的 `evaluation_score ≥ 78` 不再决定 `quality_passed`；保留为 `legacy_scores` 以便对比过渡期数据。

## 判定来源

| 层 | 规则可判 | LLM 判（需引用） | 用户判 |
| --- | --- | --- | --- |
| 合格 | R1.1–R1.3、R1.5–R1.8 | R1.4（措辞强度） | R1.7 是否仍投递 |
| 对位 | R2.2 位置、R2.4 | R2.1 状态、R2.3 | 职责权重标注（可选） |
| 优质 | R3.2、R3.3、R3.4、R3.6 | R3.1、R3.5 | — |
| 突出 | R4.2、R4.3 | R4.1、R4.4 提名 | 替换/否决 |

LLM 判定必须输出引用（bullet 编号 + 证据卡 id + JD 条目），无引用的判定视为失败而非通过。

## 验收口径

- 合成夹具只验证规则与报告结构；"质量达标"结论只能来自真实 App、真实证据池、真实目标 JD 生成的 PDF。
- 质量报告与 PDF 同版本绑定（`resume_sha256`），历史 PDF 未绑定时明示"未记录"，沿用 2026-10-13 固定 PDF 质量呈现的约定。
