# PiProofForge 核心 Pipeline 规范

## 有界 advisory 语义准备（2026-11-18）

- 每日准备计划为每条岗位返回唯一的 `recovery_action`：无可执行动作时为 `null`；可执行时为 `{kind: resume_assessment}`（来源已保存且未完成核对）、`{kind: start_matching}`（新鲜、已定位要求且无保存审计）、或 `{kind: recheck_matching, audit_digest}`（旧审计中存在有效完成项且仅匹配契约过期）。只有第三种带旧审计摘要。 匹配引擎版本更新后，旧报告不作为当前结果；仅旧审计属于已验证同形状的版本、与自身版本绑定且含结构上已完成的检查、且除契约外所有输入一致时，允许以旧摘要显式发起一次新评估，不使用旧判断或已完成项跳过当前检查。已保存失败、无有效结果、无效或其他过期的审计不因读取计划而获得动作。
- 进入页面、读取计划或刷新不自动执行恢复。点击只执行最新计划仍提供的同岗位、同动作种类且摘要一致的动作；歧义或坏形状阻断。 已通过校验的显式恢复先清除同岗位的旧内部预览及待回包标记，再执行；旧回包不能占用或替代恢复后的预览，其他岗位片段不受影响。已有 Sidecar RPC、锁、来源校验、预算及写前重验仍是实际效果门禁；计划投影不存盘，不创建新执行/审批实体，也不授予发送许可。常规补充流程及其有界续做不变。 手动「重新判断」只重新读取计划并放弃页面的临时匹配结果与预览；等待或失败不回显旧临时语义结果，成功以新计划为准。已在执行来源/恢复动作时不发起重判；其正常完成后的自动读取不丢弃本轮结果。

- 生成事实索引消费正式semantic requirements.id，兼容旧requirement_id；双字段冲突、非字符串/空ID、重复ID拒绝，不能静默丢失已校验supported/partial引用。此修复不改变preferred-card展示权重或将其称为逐事实支持。
- jobs.previewPreparation为只读内部定向事实片段，无模型/存盘/正式run/投递候选。要求同岗当前有效审计与两次输入snapshot/audit digest重验；只当前完成且非degraded/deferred父项的supported/partial引用可用，fact须与当前原事实一致。仅有资格信息、无可呈现行动/成果时blocked，不拼完整简历。复用事实质量规则、ResumePlan结构和render_plan，不走全量自动选材/职业档案扩展；同来源title/role/time上下文单独trace。partial与未完成限制保留，send_ready/active_target_eligible/deliverable恒false，不写canonical。 Daily 对即时或已保存审计若明确报告没有可用当前匹配，不发预览请求或展示当前预览入口；未记录诊断不等同已有可用片段，最终始终由预览处理器复验。

- advisory可用纯结构绑定关联唯一独立数字编号“核心技术栈硬性要求”标题、连续同格式括号子项、明确同/上级终止。仅原must_have且quote全JD唯一、精确span完整落在单个单行子项内容内时标注；nice_to_have不升级，跨行/跨子项/跨段/无标题/无明确终止/层级歧义不绑定。记录sourcehash及heading/child/quote原文与字符span；模型语义、申请门禁、canonical及模型payload/cachekey不改变。
- 可完整装入的结构绑定未核must_have批优先于普通未核must_have；已核绑定不得越过未核项。schedule主policy及v2输入快照兼容保留，新增section_policy=explicit_numbered_section_v1与来源绑定trace，仅表明检查顺序不是能力/适配判断。

- 同一有效输入快照累计checked_check_ids仅作调度历史，按当前合法check集合过滤，合并此前已核与本轮完成IDs，防多轮覆盖后反复抢占；输入变化清空。当前completed_check_ids、判断、引用与coverage仍只来自本轮有效评估/缓存，不由累计历史填充。调度trace分缓存命中、完成、预算暂缓、降级，不能把计划当实际完成或HTTP调用。

- advisory 评估调度先只读验证所有现有assess批缓存，再按未核must_have、未核responsibility、其他未核、已核批安排网络；组内原序，保留既有父子项/批内容及缓存key。不使用关键词或缺词评分。上一份同snapshot/契约且digest、schema、input_fresh有效审计中的completed_check_ids仅作排序提示，不跨新facts可见范围继承结论；坏/过期审计不影响顺序。记录调度check IDs及原因，顺序不代表适配、能力或录用判断，已核项不删除。

- 当前只读审计快照契约为advisory-preparation-v2，旧结果保留但不冒用新语义；engine VERSION和已校验批次缓存不变。阶段预留仅保证HTTP次数机会，不保证服务/解析成功，也不保证请求启动截止前仍有时间。

- advisory 专用阶段调度复用 fresh、已校正且重新通过当前偏好/JD来源校验的方向建议，不重算公共方向。canonical 默认行为不变。缓存优先且不占HTTP额度；每次实际模型调用含内容修复前检查阶段额度，recall最多使用前2次HTTP，至少留2次给assess；全量卡仍逐批检查缓存，不能用截断卡池冒充全量。
- 预算未执行的卡/检查独立计 budget_deferred，服务失败仍计 degraded；两者并集是未完成检查。只有受未完成子项影响的父要求展示unassessed，其他已验证父要求结果保留；未知父子映射保守全部未完成。无成功召回不得强造逐项判断，保存可审计未完成状态。无选中证据不等同能力不足。召回覆盖与assess实际可见事实覆盖分开披露。

- advisory 评估组同时受实际序列化输入容量与响应工作量约束；用现有结构字段上界（理由、两条可选摘录引用、可选事实 ID 与检查 ID）估计序列化字符，并对照现有输出额度，作为保守装包代理，不保证分词数或延时。正式路径不变。尽可能整父项装包，超大父项隔离分段；可装入的显式硬要求仍优先；分段统一放在可完整装入的项目之后，硬要求分段在其他分段之前。单个子项仍超出响应工作量时记为降级（answer_budget）且不发请求、不宣称可续。每个父项继续只由当轮实际完成或重验缓存的全子项决定，旧提示不代替证据。不裁切证据、不增加尝试额度，也不新增缓存存储。

- advisory 评估失败条目的诊断只记录固定原因码：请求超限、响应工作量超限、实际调用预算拒绝、本机超时、响应无效、召回前置未完成或其他传输错误。修复尝试被调用额度拒绝另作标记。保留原阶段状态、预算和验证规则，不在失败字段传播原始异常。

- jobs.matchPreparation 仅对 fresh、要求逐字定位且非方向暂缓的未批准画像复用 run_semantic_matching，不跑完整 Quick Run、不变 active/审核/发送。个人档案须已确认，使用严格已入池原证据池，legacy来源新鲜度未核验数量透明披露；不截卡池假装全量。
- 仅当前本地 Splash，HTTP 尝试最多4次、socket空闲超时20秒、90秒后不启动新请求，不是总wall-clock硬截止且超时不证明服务端推理取消；不做传输重试。原引擎逐批合法缓存可复用续做，仅本轮有缓存进展且无provider_timeout时继续，无进展停止。预算耗尽不同于服务超时；未完成召回/检查不得写成能力不足或完整匹配。结果恒 advisory_partial、send_ready=false，continuation_needed 指预算可续，不无限自动续做。
- 同一 fresh 输入快照的 advisory 匹配，应用内开始和原窗口续做共享现有审计中的预算，最多三轮、每轮最多四次实际 HTTP（含修复；可复用缓存不算 HTTP）。轮次在任何实际请求前以文件锁原子预留；预留不退，进程中断不自动重开。开始只接受无审计记录；续做仅在本次已验证可用、明确有预算未执行检查、缓存有进展且未耗尽时，携带当前审计摘要。旧记录无轮次不可推定额度。相同摘要不得重复消费，失败/超时不覆盖最近可用结果。旧契约显式重核仍独立，不恢复自动续做或覆盖失败旧结果；本预算的跨进程预留保证仅适用于普通开始与续做，不扩展旧契约重核的单次调用。
- 猎聘公开详情的已核正文须同时绑定成功详情返回的规范 URL、原始岗位 ID/类型、正文 SHA 与实际读取时间。列表搜索时间不能充当详情读取时间；跟踪参数变化不改变规范路径，路径/身份漂移使已存正文失去来源权威但保留历史正文。旧无读取证明的未审核正文不能直接进入来源捆绑准备或新增公开详情审核；同一线索可经显式成功重读建立新的依据，不自动审批；已失效的来源不会仅因恢复原路径而恢复旧审核。
- 含多个岗位描述的详情响应只读取同时匹配规范路径和原始岗位 ID 的唯一结构化正文，不复用无身份归属的页面正文。只有相关岗位时视为未取得可验证详情，不推断目标状态；推荐卡与正文中的招聘状态词不是本岗位状态证明；未归属的独立页面状态提示只阻断当前采集，不当作已下架。
- 岗位线索详情可只读查看先前保存的猎聘完整未审核 JD 正文，不为查看而重新读取平台。该文本是本机历史记录，不代表重新核验来源、确认当前招聘或建立编辑/审核绑定；仅用户显式获取才执行现有外部读取。
- 每日准备重新打开只读取。当前未审批来源草稿已有可用、明确因预算留有未执行检查且尚余轮次时，继续匹配只通过单一 `recovery_action` 返回当前审计摘要；普通岗位列表不提供摘要。只能由用户点击执行一轮，不重抓来源、不重新核对 JD、不自动连跑，不改变旧契约重核和投递。
- 结果独立保存 outputs/preparation_matching，不写原画像或 canonical matching reports。写前重验画像/lead/个人档案/偏好/证据卡及来源，读取再验；变更展示stale、损坏展示invalid。失败也保留安全原因与覆盖审计，不因全降级/无选中卡而消失。方向展示准备元数据校正值，不复活公共缓存错误排除。
- advisory 评估窗口保留合法召回引用的优先级；回补先为各来源尝试一条完整、可归责的行动或成果与已有场景/时间（职责和限定随原事实），之后再追加同源工作事实。只改变同一精确序列化预算下的事实可见性，不改变召回、正式匹配、判断或渲染。稳定顺序不保证全池覆盖；未进入窗口不等于不匹配。
- 现役引擎 shortlist 使用稳定顺序；输出 assessment_visibility 包含实际可见/遗漏事实与卡片数量和IDs，scope=bounded_fact_subset_not_exhaustive；compact个人事实也明确标识。此范围非穷尽，insufficient仅指可见范围缺证，降级检查归未完成而非能力不足。

## 规则重合预检的证据输入（2026-11-18）

- App 规则预检仅消费 status=saved_eligible、candidate_pool_eligible 显式 true 且通过既有 pool_eligible_scalars / pool_approval_reason / validated_source_inputs 的证据。排除样例、缺 title/results/artifacts 或来源明确失效卡，不把 legacy 缺审批标志视作已审核。来源 helper 返回空映射的已审核 legacy 卡按正式语义匹配兼容口径可读，但计 source_freshness_unverified_count，不冒称来源新鲜；非空校验结果计 verified_source_count。
- 每次读取重验来源，不允许只按卡文件 stat 的旧缓存掩盖材料变化；单卡错误局部排除，返回聚合 excluded_count / excluded_reasons，不暴露路径或异常原文。预检仍仅为 rule overlap，不证明满足要求或允许投递，不修改证据卡。

## 来源绑定的未批准语义准备（2026-11-18）

- 已保存准备状态经只读 `preparation` 投影复用：`state=absent|fresh|stale|invalid`、reason、`scope=input_consistency_only`、direction、requirements_grounded/count、send_ready=false。fresh 仅表示当前来源/偏好/输出与保存记录一致，不表示模型质量、完整语义或岗位适合。当前模型切换不抹去历史价值。
- 读侧共用生产者 fingerprint 算法，复用方向校验器，校验官方双向身份/原文/hash、确认偏好及来源 revision、契约/scope、方向校正记录和完整要求逐字位置。旧缺字段、损坏记录、非 avoid 的旧排除不得当 fresh。仅 updated_at 变化不失效。单项读取异常不能拖垮列表；无准备记录不加载偏好来源，同一列表调用只加载一次。
- 计划行透传准备状态；draft+fresh 显示 `preparation_saved_unapproved` 或 `preparation_direction_deferred`，stale/invalid 显示重新准备原因，仍留 deferred，不增加selected、不减少shortfall、不创建人工逐项待办、不解除任何投递门禁。读取不写文件、不调用模型。


- `jobs.assessPreparation` 仅处理与官方线索双向绑定、身份/原文/指纹一致的未批准 draft；偏好须确认且来源校验通过，仅调用当前明确配置的本地 Splash，不向远端发送偏好。
- 冻结画像内容、线索内容及偏好 revision；方向建议复用原验证器，aligned 不得引用 avoid 项。方向仅为建议，不等于能力匹配或投递批准。仅方向 excluded 且引用 avoid 项时保存建议与绑定元数据并暂缓自动提取，不修改旧语义字段；excluded 引用 primary/bridge/explore 时有效建议降为 needs_review，保存原 model_direction 和校正原因并继续严格提取，不能把无回避依据的模型推断当自动排除；这是自主准备优先级，不新增手动流程禁令。
- 新编排的严格提取模式要求 must_have/nice_to_have 为原文逐字条款，逐项保存原文 start/end 位置。不能定位时不保存，不生成假依据或为过校验改写事实；手动生成默认语义不变。原文定位证明可追溯，不证明分类或语义蕴含正确。
- 写入前重新校验冻结输入，变化则拒绝覆盖。结果存回原画像 preparation_json 及语义字段，状态仍 draft，review 保持空，active_target_eligible/send_ready 恒 false，不自动审批、不发送。
- 本编排沿既有方向校验最多一次内容修复，JD 提取不增加修复循环；记录模型阶段调用计数（不代表底层 HTTP 重试次数），单请求 timeout 不超过60秒，错误返回受控原因码；现有方向缓存可复用但不等同于本次画像已保存。同入口重入拒绝；不宣称跨进程写入的完全事务原子性。

## 有界候选来源补充（2026-11-18）

- 已确认查询含明确软件角色（如 Tech Lead、软件/后端/前端/系统开发）时，在每路结果内部稳定软排序后分配既有详情预算：明确软件工程标题优先，未知内部平台职责保留，其次明确生物/销售等非软件标题。软件工作即使属于制药或销售业务也不因行业降级。无软件方向依据时维持原顺序；不从个人技能推断方向，不加入 Java 必选条件，不删除任何结果，不改变身份/城市/已投门禁，也不据排序宣布适配。每路宽查询与 2 次搜索、最多 3 次详情的上限不变。

- 搜索词由确认主投偏好中的连续角色原文与独立档案城市派生：显式 Tech Lead / 平台负责人可短化，其他安全首分句兼容；角色 trace 保留偏好 index/revision/quote 与原 text 字符位置。纯编排不改偏好、不新增配置账本、不发送 trace。现已核官方 SearchJobInput.address 可选字符串及 README 北京示例（https://github.com/liepin-tech-2026/liepin-cil/blob/main/liepin_cli/models/job.py ，README.md）。角色单独作为 jobName，确认城市归一化后经 address 传入；不造 city/category 参数，保留本地城市复核，不声称已实证服务端过滤质量。旧省略 address 的调用维持原 payload；显式空白、非字符串、控制字符或超过100字符拒绝，不默默回退无地域搜索。query_plan 每项返回 address，trace仍仅本地返回。
- 技术锚明确 technology=null、technology_reason=primary_stack_not_structured；资料出现某技术不等于确认主栈，本片不推断/枚举技术、不新增候选技术硬过滤。最多两个去重查询，结果回传 query_plan 是计划，queries 仍只记录实际请求；单查询分页与单详情槽从首路开始，行为不变。两路独立确认查询且详情余额至少 2 时，先读取首路最多余额减 1 个详情，为次路保留最后 1 槽；次路搜索成功但没有新的可尝试线索时，用首路保留线索回补并重验身份、城市和尝试记录。失败详情也消耗预算；只按实际尝试身份去重，不把已保留线索标记成已尝试。次路可能返回与首路重叠的线索，此调度保证查询机会，不保证唯一岗位召回改善。搜索未通过、遇到明确登录限制或安全验证时停止进一步外部请求，已获取的条目保留。

- `jobs.replenishPreparation` 是显式本地写操作，不能从页面加载或只读 `jobs.planDailyPreparation` 隐式执行。根据现有准备缺口和来源有效的已确认主投偏好、档案城市构造少量查询，不发送资料原文/引用/联系方式，不从历史岗位猜新意向。
- 一次 maximum=1–3 是来源准备上限而非合适岗位或投递承诺；最多2次官方搜索、3次详情抓取。复用官方搜索稳定身份导入、公开详情身份/正文核对与未审核画像转换，不走旧浏览器搜索、不加外部平台或模型重试。
- 本地筛选同城且未归档/拒绝、无已有画像关联、无历史尝试占位、批内不重复的官方候选。未知城市/身份、历史损坏或偏好来源失效必须明确暂缓/失败；搜索为空或部分写入不得冒充完整成功。已有画像及人工编辑不覆盖。
- 来源验证只证明岗位身份、完整正文及指纹一致，不证明语义适配或允许投递。结果区分received/imported/source_prepared/deferred/errors，恒send_ready=false，未自动代填approved。库存已有leads不得阻止存在缺口时的补充。
- 同入口重入拒绝，逐候选写入前复核绑定/状态，变化时跳过；不宣称与其他进程编辑完全原子。界面展示实质阶段结果与错误，不要求用户逐项替应用选择，不在操作成功后自动发送。

## JD 结构化请求预算与失败语义（2026-11-18）

- JD 草稿请求复用 `JOB_PROFILE_DRAFT.capability.max_output_tokens` 的 2048 token 预算，不因通用兼容 provider 而无上限。
- 方向评估与 JD 沿下述统一请求控制配置；Splash 的明确关闭由现有设置传播为 `reasoning_effort=none`，不再按固定部署地址自动注入。handler 不重复设置协议字段，结构化输出预算与严格校验保持独立。
- `finish_reason=length` 必须返回 `parse_output_truncated` / `output_truncated`，正文即使能解析也不可成为可审核草稿；给出缩短 JD 或检查结构化输出设置的提示，不错报连接失败。
- 不新增模型重试、自动审核或投递；成功草稿继续保持非 active target。真实服务成功与单测通过分别记录。

## LLM 请求控制配置（切片 L3b）

- 复用现有 `thinking_enabled`（`boolean | null`）与 `thinking_effort`（`low | high | max`，默认 `high`）。`null`/字段缺省表示 provider 默认，`false` 为明确关闭，`true` 为明确开启；强度字段本身不能开启思考。已保存布尔值按当前明确配置读取，不猜其历史来源，不增加能力表、配置账本、部署绑定字段或兼容分支。
- 优先级为调用方显式 payload 参数 > 当前调用的明确配置 > provider 默认。结构化 JSON 只约束输出形状，不覆盖明确的思考配置；不通过 URL、模型别名、量化名称或样例内容推断请求能力。客户端不修改响应以掩盖不支持的参数。
- 泛兼容路径（含 OpenAI、OpenAI Compatible、LM Studio）默认不附加可选 thinking/reasoning 参数；明确关闭请求 `reasoning_effort=none`，明确开启请求配置的强度。显式控制是调用方对协议参数的选择，不证明服务已支持；服务拒绝时保留原错误，不探测、不删字段重发、不改模式。LM Studio 既有原生 schema 适配继续承担结构协议。
- 已有 provider 协议默认保留：DeepSeek 默认/关闭使用 `thinking.type=disabled`，明确开启使用 enabled 与强度；Strata 默认/关闭使用顶层 none，明确开启使用 low/high，max 映射 high。两者均尊重显式 payload，JSON 请求同样尊重明确配置；其他 provider 不由客户端生成 DeepSeek thinking 对象。
- `settings.update` 在相同部署内省略字段为保持、显式 null 为重置。部署由实际 provider 和归一化后有效 base_url 确定；两者任一改变时，未在本次明确提供的控制恢复默认，明确字段仍按本次请求保存。单独提供强度不确认旧开启状态；仅改变模型别名不修改控制。复用原配置存储，不建立按模型或部署的历史映射。
- App 配置读取时缺省/null 都采用 provider 默认，不继承父进程 thinking 环境；直接构造必须保留 null，不能 bool 转换或任务内硬写 false。客户端构造省略模式参数时才沿 CLI 入口读既有环境，明确传 None 不读模式环境；可用私有未提供哨兵区分，不能引入另一个公开配置字段。Quick Run 沿原 `LLM_THINKING` 传 on/off/default，使 default 覆盖父进程 on/off；不新增环境变量或第二传播路径。
- 设置页面沿同一字段提供默认/关闭/开启，并对实际部署改变复位；普通同部署保存与模型切换保持该配置。完整表单保存明确提交地址；空白地址沿 API 现有非空校验拒绝并展示错误，不能省略后静默保留旧地址或宣称切换成功。直接调用、结果复审、方向/JD、preparation 有界客户端与 Quick Run 子进程必须消费同一已解析配置；模型列表请求不把思考参数当作能力探测。
- 验收先以实际 Request 复现旧端点/型号默认、null 复活父环境、部署切换残留、明确开启被 JSON 覆盖与传播丢失，再保住显式 payload、provider 协议、schema、预算、原 HTTP 限额/localhost/重定向边界。应用端使用全合成资料与明确配置的本机 Splash；不把协议夹具或参数对照当作真实模型验收。

## 概述

PiProofForge 是一个 evidence-first 框架，将原始工作材料（日志、PR、报告、截图等）转为结构化证据（Evidence Cards），再通过可解释匹配生成事实保真的目标文档（简历等）。

系统目标不是维护一份所有岗位通用的静态简历，而是基于用户真实个人资料、工作经历和 Evidence Cards，结合目标公司、岗位 JD、must-have、seniority signal、业务场景和简历定位，生成可投递的候选人简历版本。同一版本可以复用于同类岗位或同一目标岗位簇，但不得被定义为“一份简历投所有公司/岗位”。

### AI 任务共同上下文（2026-10-20）

- 所有 App/CLI 模型任务共用一份产品级指令，由现有 LLMClient 在发送对话请求时统一加入 system 上下文；保留任务自身要求、输出格式和输入数据，不能把资料正文提升为指令。该指令从产品愿景提炼，不直接拼接用户的口语要求，不创建第二套模型调用框架。
- 以用户主动纳入的职业资料为分析起点，主动关联人物、任职、项目、行动、时间和成果；省略“我”不等于没有个人贡献。结合文档标题、章节主体、已确认档案及多份材料判断归属，区分本人贡献、团队成果、系统能力、第三方案例和计划。
- 提炼/补全阶段可给出带原文依据、置信度与责任限定的候选；待确认推断不得当成已审核事实用于简历。区分项目期间、任职区间、文档整理时间、单次事件日期及示例数据，不能用方便取到的日期补齐项目期间。
- 匹配/选材/评估以目标 JD 和可证明的贡献为依据，在现有输出字段内说明价值、缺口或补证优先级；缺证据不等于无能力，也不等于该经历永久不适合展示。先完成有界资料分析，再提出最少且具体的确认事项；不自动审核、发送或发布。
- 公共指令内容的指纹进入方向评估、语义匹配、证据推断和质量判项缓存；任务提示词或输入上下文变化时，旧判断不冒充本轮新判断。提示词优化不放宽来源校验、字段可信等级或投递授权。

## 核心实体规范

### Evidence Card

```yaml
schema: evidence_card_v1
required_fields:
  - id          # 唯一标识，格式：ec-YYYY-MM-DD-NNN
  - title       # 简短描述
  - raw_source  # 原始材料路径或引用
  - results     # 可量化的成果（必填，否则不进入候选池）
  - artifacts   # 关联产出物（必填，否则不进入候选池）
optional_fields:
  - tags        # 技能标签
  - period      # 时间范围
  - context     # 背景说明
```

**约束**：`results` 或 `artifacts` 任意一项缺失，该 Evidence Card 不进入匹配候选池。

### Job Profile

```yaml
schema: job_profile_v1
required_fields:
  - id          # 格式：jp-YYYY-NNN
  - title       # 岗位名称
  - keywords    # 关键词列表
  - level       # 级别信号（junior/mid/senior/staff）
optional_fields:
  - tone        # 语气偏好
  - must_have   # 硬性要求
  - nice_to_have # 加分项
```

### Matching Report

```yaml
schema: matching_report_v1
required_fields:
  - job_profile_id    # 关联岗位
  - evidence_cards    # 入选证据卡列表（含分项得分）
  - gap_tasks         # 缺口任务列表
  - score_breakdown   # 各维度得分（必须可解释）
```

## Pipeline 阶段规范

### 阶段 1：证据提炼（Evidence Extraction）

**输入**: 原始材料文件（txt/md/pdf）  
**输出**: Evidence Cards（YAML 格式）  
**工具**: `python3 -m tools.cli.entrypoints extract`（规则或 `--use-llm`）  
**约束**:
- 不得推断或补充原材料中没有的信息
- 每个 Evidence Card 必须有明确的 `raw_source` 引用

工作目录材料接通（2026-10-05）：复用材料库已有 `# Source:` 文档边界，为已导入的 TXT/Markdown 提供按名称筛选、选择原文片段和预览；只读取库内已有材料，不追踪原文里的本机路径或指令。模型提炼使用选中的有界文档（单次最多 24000 字符），过大时明确要求选择较小片段，不静默截断全文，不把整个目录汇总不加选择地交给模型。继续复用现有提炼草稿、人工审核、results/artifacts 来源校验和保存入口；新草稿记录所选文档标识/指纹，保存时重验内容未变且结果确实来自该文档。未审核卡不得进入生成。文档中的任务指令仅为数据，不能成为执行指令。

### 阶段 2：匹配评分（Matching & Scoring）

**输入**: Evidence Cards + Job Profile  
**输出**: Matching Report  
**工具**: pipeline 内部逻辑  
**约束**:
- 所有评分维度必须有对应证据支撑
- 缺口任务必须明确列出（不得静默忽略）

P0-026 证据约束的语义匹配（2026-10-12，用户已同意）：
- Quick Run 的 LLM 匹配复用配置好的模型和客户端，将全部合格 Evidence Cards 按卡数/文本量分批评审，不再按关键词截去候选。只传标题、场景、职责、时间、行动、结果、技术栈等原始事实；每批回包必须逐卡覆盖，无未知/重复/遗漏 ID。
- 第一阶段逐卡给相关度、理由、关联的 JD 要求及原文引用；第二阶段汇总语义相关原文和已确认职业档案的必要事实，对每项要求给出 `supported` / `partial` / `insufficient` / `conflict`、引用和理由。学历、年限、本人职责不能由相似技术或他人经历推断；未找到证据不等于候选人不具备能力。
- 引用须包含事实 ID 与原文，程序校验来源、字段与原文包含关系；非 `insufficient` 判断必须有有效引用，未知 ID、伪造原文、遗漏要求、非法状态/分数全部拒绝。引用校验只证明来源存在，不冒充语义判断已获人工确认。
- 语义结果独立保存为匹配报告同名 `.semantic.json`，绑定岗位、证据和必要个人档案的 SHA256、模型与版本；同输入/模型/提示词复用已校验缓存，输入变化不复用，失败批次不发布完整结果。严格 LLM 模式失败明确阻断，不静默回退成语义成功。
- 模型 JSON 或引用不合法时，每个请求最多允许一次带校验错误的纠错；第二次仍不合法即失败，失败响应不进缓存。网络超时不在此处自动重试；记录实际模型调用、纠错与缓存次数，输出长度和条目数量受限。
- 缺引用的正分卡/非不足要求，错误须列出本批全部受影响卡或要求编号。纠错明确要求补真实原文引用；确实无引用时改为零分且无关联要求/insufficient，不保留无引用的正向判断，不增加重试次数。
- 已确认职业档案的补充成果（名称、说明、链接）纳入语义事实输入，按独立的个人/开源项目语境引用，不推断为任职单位生产落地；未确认的档案不参与。
- 语义评审仍覆盖全部合格卡，代表项目在有可用完整事实时优先从角色、时间及任职关联均通过既有校验的卡中选择，最多三项且不以缺项卡补足数量；将拟展示项目的完整事实同时提供给逐项要求评审，同等支撑力度优先引用这些项目；不能为了呈现而提高结论。未入选卡支撑的要求保留简历未呈现缺口，不提高匹配结论。无完整卡时保留原待补草稿路径。
- 生成复用已验证的语义选材，仍从原字段拼装 A/B 与独立 trace，不重复调用模型选同一组卡。评测复用匹配结果，不再额外调用解释模型；分别输出证据池岗位适配、实际简历要求覆盖、事实完整性与表达质量。证据池有引用但简历未呈现时记为 `not_present`，不得算简历已覆盖。
- 选材优先保留 supported / partial 要求真正引用的卡（每项权重 2 / 1，同分再按模型相关度），仍最多三项；正文行动/结果优先展示被引用的完整原字段，再沿用旧排序和数量上限，不为了词面命中改写事实。
- 要求评审使用明确的评估日期；单项结论仅按该项 JD 判断，“或”不扩为同时满足，个人项目不自动等于企业生产经验，也不能在 JD 未要求时额外强加生产门槛。已识别的年限比较自相矛盾、额外年限/生产条件由校验拒绝，沿原每请求最多一次修复；失败保持阻断，不能把错误分数作为有效结果。
- 规则模式保留词面指标；语义模式下关键词覆盖只作辅助，表达质量按原非关键词分项权重归一化，参考线仍为 78。质量通过仍要求事实完整、追溯有效、PDF 就绪、表达质量达线，且所有要求已支持并在简历呈现；任何 partial/insufficient/conflict/not_present 都保留具体缺口，最终人工审批与投递授权不变。
- Quick Run 默认使用语义模式，模型失败显式报错；保留可选规则模式用于离线基线。现有结果区显示模式、证据覆盖数、岗位适配/简历覆盖/表达质量及可展开的要求、理由、原文来源。历史规则结果兼容。首轮只接通真实 Quick Run 调用链，Agent 简化循环不冒充已完成相同迁移。
- 使用同一冻结证据池，对照多种测试画像与规则基线，记录选卡差异、逐项判断、耗时、调用/缓存次数及事实阻塞；样本须为明确合成或另行获准使用的材料。本地模型/handler 实测不替代真实页面深度验收。暂不安装 embedding 模型、向量数据库或新依赖。

### 阶段 3：文档生成（Generation）

完整职业简历实施（2026-10-05，用户已确认开工）：

- 正式正文的项目行动/成果及工作经历职责/成果以已选的精确 Fact 为单位渲染；合并或去重不能把一个事实的来源记作另一个。生成追溯记录所渲染的事实 ID、来源、字段和实际行号；对位与首屏只使用该精确呈现事实，不以同卡文字片段、相同措辞或模型行号替代。旧无精确追溯仍可历史查看，重新评估不得把旧结果当作当前覆盖。
- Quick Run 的证据引用检查复用现有 `read_generation_trace` 核对正文与输入指纹，再按 `claims` 检查每条简历 bullet 的完整事实文本是否由个人资料或证据字段组成；岗位描述、自定义求职定位、数字和技术词本身不能代替追溯。缺失、过期或无效 trace 按未验证处理，不得获得引用分。
- Scorecard JSON 与 Markdown 同步记录关键词命中/缺失、硬性条件待核对和逐 bullet 追溯结果；保留既有总分权重、参考线、缺证据与人工审批门禁。历史已生成/已批准产物不覆盖，复测结果另存。
- 生成读取证据时，`role_scope` 中由模型输出留下的 `[]` / `{}` / `null` / `None` 空值标记按缺本人职责处理，不生成“角色：[]”，也不能通过非空字符串检查。原证据文件不自动改写。

### Agent Loop 扩展阶段（用于 Autonomous Agent）

以下阶段属于 Agent 编排扩展，不改变核心 pipeline 的 evidence-first 约束：

- `DISCOVER`：从 `job_leads` / `jd_inputs` / `evidence_cards` 推导候选方向与 JD
- `GATE`：联合判定 matching / evaluation / channel readiness
- `REVIEW`：投递前审批（auto 模式 pass-through；manual 模式暂停展示 TopN 候选，等待用户 approve/reject/skip）
- `DELIVER`：通过通道执行投递
- `LEARN`：根据本轮失败原因调整下一轮输入与策略

约束：
- 扩展阶段不得绕过 Evidence Card 校验与事实保真约束
- 所有投递与门禁结论必须写入可追溯 run log
- policy 必须支持企业例外清单（company exclusion list），用于排除不应进入投递链路的目标企业
- 企业例外清单应在 `DISCOVER` 阶段主过滤，在 `GATE` 阶段做兜底校验
- REVIEW 阶段在 auto 模式下为 pass-through，不影响既有行为；manual 模式下暂停等待用户决策

## CLI 接口规范

### 招聘平台接入契约（2026-09-27，待实施增量）

本节定义新接入的目标契约；2026-09-28 官方只读 P0-011 已接入并通过真实原生验收，投递及多平台增量仍待实施，旧浏览器/CLI 路线保留兼容。实施次序以 `docs/execution-roadmap.md` 为准，依据见 `AIEF/docs/plans/2026-09-27-recruitment-platform-integration.md`。

- 正式覆盖六平台：猎聘、BOSS直聘、智联招聘、前程无忧 51job 为核心来源，脉脉、拉勾为补充来源。六家均进入计划与验收范围，后续按平台单独记录进度，技术阻塞不自动删除目标。
- 六平台共同最低能力为可追溯岗位输入、完整 JD、画像审核、可解释匹配、定制简历版本关联和结果追踪；每平台至少 1 个真实来源样本验证。入口复用现有 Jobs/Quick Run/Submissions，不因平台扩展增加独立业务流水线。
- 四家核心平台目标包括在线只读搜索与详情；脉脉、拉勾首版采用职位链接和完整 JD 导入。来源覆盖、在线只读、真实投递、平台反馈同步分别验收；人工导入/手工反馈须标明来源，不能满足在线接口或投递成功验收。
- 猎聘官方 HTTP 为首选传输；CLI/MCP 不与 HTTP 平行实现第二套业务流程。第三方 BOSS/智联工具须固定经核对的版本，并以该版本能力清单决定可用平台；不假设最新版保留旧平台。
- 认证 readiness 按实际传输验证：官方 Token 由后端只读调用确认；浏览器由真实会话确认。不得用浏览器 profile 存在代替 Token 有效，也不得伪造浏览器步骤满足 API 通道验收。
- 官方岗位摘要导入须保留上游 `salary` 与 `location` 原文并在岗位线索中展示，供用户理解岗位条件与筛选；缺失显示未提供，不推算工资或将薪资上限当保证收入。重新搜索更新这两项，同时保留既有完整 JD、审核和画像关联；未知字段类型明确拒绝导入，不把结构化对象转成伪薪资文本。
- Token 仅进入后端受控凭据通道，并仅向核实的官方 HTTPS 请求注入认证头；前端回读只显示配置/验证状态，日志/审计中的请求头副本必须脱敏，子进程参数、产物与版本库不含密钥。首个切片仅允许岗位搜索和简历读取，不开放简历修改、聊天、投递或反馈写操作。
- 2026-09-28 用户指定猎聘 Token 不接入钥匙串，接受本地明文权限文件。macOS 固定保存到 `~/Library/Application Support/PiProofForge/credentials/liepin-token`，凭据目录 `0700`、文件 `0600`，不随工作目录或调试 App 标识变化；不写入仓库、普通配置、前端持久化或日志。拒绝符号链接、非普通文件及不安全权限；写入须原子替换，失败明确返回且不得假报成功。
- 凭据在后端首次使用时从本地文件恢复为 `unverified`，只有真实只读请求通过才为 `valid`；正常退出只释放内存，用户主动删除才删除文件。保存/读取/删除失败返回 `CREDENTIAL_STORAGE_ERROR` 固定安全信息，删除失败不得显示已删除；非法新输入不得销毁原有保存项。测试必须使用隔离目录与合成 Token，禁止读取或清理用户真实凭据。
- 复用 Job Lead/Candidate/Job Profile；补齐平台、稳定岗位 ID、平台原始岗位类型、详情引用、获取时间与 JD 完整性。猎聘 `jobType` 按原值校验后映射到 `jobKind`，不得硬编码；列表摘要不能当完整 JD，无法获取正文时走人工补齐和审核。
- 适配器校验 HTTP/CLI 传输结果、业务码/`ok`、payload 三层。`ok=false`、非 JSON、认证失效、空数据和平台不支持分别表达；不得将错误对象映射为岗位，也不得静默降级为“在线查询成功”。
- `DeliveryRequest` 必须使用明确的平台路由，业务方向不能充当渠道。仅配置读取来源不启用该平台投递。结果未知时不自动重试写请求、不切换邮件补投；其他跨渠道发送也必须在授权范围内。
- PDF 版本/指纹、平台实际发送的附件或在线简历身份、审批记录须可关联。接口只有岗位参数不构成版本绑定证据；无法核验时保持阻断，不自动覆盖在线简历或降低为默认平台简历。
- 复用 `SubmissionRecorder` 与 External L3，新增适合 API 的认证、目标、版本绑定、提交和回执证据契约；未知/失败/重复/成功分别记录。无权威业务成功依据时 `DeliveryResult.success=false`。Token 接入不得沿用“原始密钥 env 进入 L3 模板”的做法，应通过后端凭据引用解决。

#### 人工导入来源契约（2026-10-11，S7 脉脉 / 拉勾首版，BOSS / 智联 / 51job 人工导入同用）

- 来源链接按域名识别平台并记录 `platform`：`maimai.cn` → `maimai`，`lagou.com` → `lagou`，`zhipin.com` → `boss`，`zhaopin.com` → `zhilian`，`51job.com` → `qiancheng`，`liepin.com` → `liepin`，其余 → `other`。识别只看域名，不向平台发请求。
- 人工导入（用户粘贴完整 JD，可附来源链接）保存为完整画像时，对 `maimai`、`lagou`、`boss`、`zhilian`、`qiancheng` 的来源链接只做 HTTPS 语法校验，不做可达性 GET（平台协议禁止脚本访问，且会触发登录或验证页）；`source_url_check.status` 记为 `manual_platform_not_checked`。其他域名沿用现有可达性检查。
- 人工导入的画像与线索记录 `import_mode: manual`、`platform` 与 `source_recorded_at`（用户保存来源的时间）；线索 `source` 保持 `manual_jd`。界面在画像卡、画像详情与线索列表标明“人工导入 · 平台名”。
- 仅链接不算完整 JD：`source_jd` 为空或只是 URL 时保持 `missing_jd_text`，不能保存为完整画像。
- 来源覆盖、在线只读、真实投递分别验收：人工导入样本计入来源覆盖，不表示该平台具备在线只读或 App 投递能力。人工导入平台的投递只能由用户在 App 外完成，并以“手动投递记录”形式回填（见下条）。
- 手动投递记录：用户可为任一画像记录一次 App 外完成的投递（平台、投递时间、可选简历运行编号与备注）。记录写入 `outputs/submissions/<platform>/<run_id>/submission_log.json`，`channel` 为平台码、`transport: manual`、`mode: manual`、`status: manual_recorded`、`receipt_source: manual_tracking`，步骤只有一条 `manual_record`；列表与详情标明“手动记录”，不计入 App 自动确认数，不可重试，可作为反馈迭代的关联投递。

#### 真实投递结果与反馈收口（2026-10-01）

- Submissions 详情统一展示两条 App 路线的审批运行、岗位、简历版本/指纹、回执来源与本地证据完整性。完整性检查只读已有批准快照、业务回执和 SQLite 尝试记录；缺失、被改动、结果未知或仅外部观察时不得显示核验通过，也不得改变原投递状态或补发。
- External L3 增加显式的已存 App 投递验收入口，复用相同证据检查及原真实页面证据。该入口只接收提交编号，始终禁止新网络提交；旧浏览器实时执行入口保留独立适用范围，不能以其 session/PDF 门禁阻断官方 API 历史记录。报告保存原日志、快照与回执指纹，不复制凭据、招聘者标识或签名 URL，不改写原日志来制造反向链接。
- 真实发送结果使用 `submission_receipt` 反馈来源，不冒充 check-mode 结果。用户在选定投递记录后可填写人工招聘反馈或个人复盘，明确标记来源；系统不得自动编造招聘者评价、回复或已读事实。反馈记录从服务端绑定原提交/审批/岗位/版本/回执，重新进入页面可读回；客户端提供的其他提交反馈不得混入当前记录。
- 对受控真实投递，反馈动作记录为下一轮计划，可指向原岗位画像、证据补全或 Quick Run；不复制同一 PDF 冒充重新生成版本，不更改旧简历、审批、回执或额度。实际再生成仍使用现有 Quick Run 与审核链，反馈保存不会自动发起生成或投递。原检查模式兼容入口保留。
- 2026-10-11 投递反馈回流：官方接口不提供投递进展，平台进展只能由 App 自有已登录会话只读读取。同步限定 `c.liepin.com` / `www.liepin.com` 下的用户中心与投递记录页，先发现链接再读取页面，不点击“聊一聊 / 发简历 / 发送 / 投递 / 删除”等业务控件，不发消息，不改平台简历，与原生 PDF 操作共用互斥。观察按岗位编号匹配投递记录（无编号时公司+岗位唯一精确匹配），状态按关键词归一化为 delivered/viewed/interested/interview/rejected，其余保持 unknown；结果只追加到各记录的 `platform_feedback.json` 历史，回执、日志、批准快照与尝试记录不变。找不到记录页时记录 `records_page_not_found` 与脱敏候选链接，不猜测状态。反馈项增加 `platform_delivery_status` 来源并给出下一轮动作建议；总览 `feedback_funnel` 只统计最新状态与未同步数。

#### 生成 PDF 补充授权与原生登录兼容性（2026-09-30）

- 2026-10-12 指定岗位的单次授权：用户确认具体岗位与已固定 PDF 后，可在 App 显式登记本岗位一次投递，复用独立补充批次，额度固定为1；旧批次需已耗尽且没有未决/进行中记录，旧额度及历史不重置。授权引用绑定审批运行、岗位键和PDF指纹，其他运行/岗位/文件不能消费；重复登记不补额度，沿既有全局防重与上海每日最多3次守卫。单次授权不启用持续任务、不扩到其他候选。

- 2026-10-12 新版附件页兼容：支持官方新 CSS-module 附件卡与既有 React attachmentResume 元数据。若平台不再返回旧独立附件列表接口，必须同时具备本次上传/保存成功回执、唯一当前附件卡与上传 fileId/名称/大小/附件ID一致、浏览器实际下载 HTTP200 且字节长度和SHA256精确匹配批准PDF，才可绑定；无原列表回执时不接受下载403/失败的降级。旧列表出现但失败或有冲突时仍拒绝。检查只读，不重传，不改批准文件和授权范围；核验失败在App结果区明示。

- 只有用户明确授权上传可能带来的在线简历解析补全及后续投递携带附件等效果后，才可按该次具体岗位与 PDF 的授权执行。待上传 PDF 须先固定为只读快照，经 App 明确批准后执行账号附件上传；不得据此重开或扩大既有批次。
- 原生上传适配只接收受审核运行引用；后端验证真实生成追溯、Lead/Profile 和文件指纹，不能由前端提供任意本机文件/脚本。上传开始前持久化 in-flight 状态，未知不自动重传；上传成功与岗位投递成功分别记录。平台附件标识及内容绑定无法核验时，不调用岗位发送。所有观察由 App 执行并保存有界脱敏证据，不以开发者网页点击或人工填成功回执替代。
- 当前真实前端限制文件名（含后缀）不超过 24 字符。旧适配器生成 27 字符名称且没有上传响应时，只有 App 观测到同一官方资源版本，并只读核实其 SHA256 与上传前拒绝规则，才可把该次未知归类为客户端未发送；保留原观测和版本依据。修正短文件名后沿同一批准快照继续，不重新批准内容、不把校验恢复算成功。
- 附件绑定以发送前本机字节 SHA256、浏览器上传成功响应的 filePath/长度、附件保存成功和当前唯一附件记录的 fileId/encryAttachmentId/文件名/长度共同证明。回读下载是额外核验，403/CORS 不冒充字节回读成功；若成功回读却 hash 不同必须阻断。岗位投递仍须核对目标、具体附件及独立业务回执，上传成功不能代替。
- 目标页仅提供“聊一聊”时，App 在进入沟通前核对最新 JD/审批快照/附件绑定并取得既有 SQLite 的 generated_pdf 单次占位；进入沟通可能包含平台自动招呼，属于同一次已授权流程。阶段观测与最终附件发送分开记录，打开沟通不算 PDF 成功；跨重启不得再次点击开始沟通，未知占用名额且不得换岗重试。
- 最终发出请求时绑定随发送历史冻结，`final_send_pending` 与 `success` 阶段的当前附件检查不得覆盖或删除它；历史回执核验只读既有证据。签名附件 URL 仅可在 WebView 下载内存中保留，序列化和后端落盘均去 query/fragment，包含嵌套 JSON 字符串；不将签名写入审批/运行产物。
- 2026-10-01 新增多岗位真实验证：账号可保留多份附件。绑定须在上传成功所指 fileId、批准文件名/长度和当前附件卡片之间唯一匹配，再核对下载字节；不得依赖账号仅有一份附件，也不得选账号默认项代替目标文件。进入发送确认框后，App 仅可选择唯一匹配已批准 fileId 的单选项；最终发送仍重新检查该选择、岗位和会话。重复身份、缺失或内容不符保持阻断，历史已发送绑定不变。
- 平台上传后可自动转到 `/resume/parse-result`。App 检查会话时仅在这个固定官方页面且没有登录表单/安全验证时，正常导航回 `/resume/edit` 并重新检查正向登录信号；不确认、跳过或补写解析表单字段，不把原解析页 URL 当认证成功。其他未知页面、空白、登录与安全验证保持原阻断。

### 岗位适配预检与推荐排序（2026-10-22）

目的：在逐个跑 Quick Run（真实全链 12–29 分钟）之前，用低成本预检判断“哪些岗位值得跑”，避免把低匹配岗位送入授权投递。

- `jobs.listProfiles` 的每个画像增加 `fit_precheck`，只作推荐参考，不阻断生成、审批或投递；保留 `fit_state` 字段，但旧评分卡没有四层 `tiers.fit` 时由旧的 `failed` 改判为 `unassessed` 并退回规则预检，不能把历史结果冒充已预检失败。
- 预检优先级：**可信 assessed 优先，否则规则预检**。
  - assessed 仅在最近 matching report 对应的 scorecard 具备四层报告 `quality_report.tiers.fit`（明确 `passed`）时可信；failed 态还必须有语义评审 `semantic_review.fit_score`（0 是合法显式分）或带有合法 `recommendation` 的 `delivery_advice`，空建议对象或仅四层报告不算可信。旧评分卡没有四层报告时不得谎报“已预检失败”，退回规则预检。可信 assessed 的 `state` 优先取 `delivery_advice.recommendation`（apply→recommended、strengthen→consider、reconsider→caution、fix_facts→hold）；无建议时以 `fit` 通过为 recommended，未通过时结合语义适配分与缺口数给出 consider/caution/low。

## 统一核心引擎架构规范

> 本节由架构审核确定（v2，2026-03-06 审核修订），适用于所有新增模块与重构变更。
> v2 修订基于六边形领域核心、策略注册表、管道组合化、配置解聚、Result 类型、事件溯源六项架构改进。

### 核心原则

1. **零 subprocess**：所有阶段通过纯 Python API 调用，禁止 subprocess 串联。
2. **DRY**：LLM 客户端、YAML 解析、配置管理、错误处理各有唯一实现，不得在各阶段重复。
3. **OCP**：规则/LLM 实现通过策略注册表（EngineRegistry）动态注入，新增策略只需注册，不改已有代码。禁止在业务逻辑中出现 `if use_llm` 分支。
4. **可测试**：领域逻辑不依赖 IO 与第三方服务，可独立单元测试。
5. **依赖倒置（DIP）**：所有模块向领域层"内指"，领域层零外部依赖。Protocol 定义在领域层，实现在外层。
6. **组合优于继承**：Pipeline 由 Stage 对象组合而成，agent_loop 复用 pipeline 的 Stage，而非继承。
7. **接口隔离（ISP）**：各组件只接收自己需要的配置切片，禁止传递上帝 Config 对象。

### 架构分层（六边形领域核心）

依赖方向：`cli → orchestration → engines → domain ← infra`

```
┌─────────────────────────────────────────────┐
│  cli/           入口层（唯一读取 env/argv）    │
├─────────────────────────────────────────────┤
│  orchestration/ 编排层（Stage 组合调度）       │
├─────────────────────────────────────────────┤
│  engines/       引擎层（Protocol 实现）        │
│  channels/      投递通道层                    │
├─────────────────────────────────────────────┤
│  domain/        领域核心（零外部依赖）  ← 核心  │
├─────────────────────────────────────────────┤
│  infra/         基础设施层（向内依赖 domain）   │
└─────────────────────────────────────────────┘
```

```python
# engines/registry.py — 新增策略只需注册，不改已有代码
T = TypeVar("T")

class EngineRegistry(Generic[T]):
    def __init__(self) -> None:
        self._factories: dict[str, Callable[..., T]] = {}

    def register(self, name: str, factory: Callable[..., T]) -> None:
        self._factories[name] = factory

    def create(self, name: str, **kwargs: Any) -> T:
        if name not in self._factories:
            raise ValueError(f"Unknown engine: {name}. Available: {list(self._factories)}")
        return self._factories[name](**kwargs)

# 各引擎自注册示例
```

### 管道组合规范（Stage 模式）

```python
# orchestration/stage.py
@dataclass(frozen=True)
class StageResult:
    success: bool
    data: Any
    errors: tuple[PiProofError, ...] = ()

class Stage(Protocol):
    name: str
    def execute(self, context: RunContext) -> StageResult: ...

# orchestration/pipeline.py — 线性管道：Stage 的组合
class LinearPipeline:
    def __init__(self, stages: Sequence[Stage]):
        self.stages = stages

    def run(self, context: RunContext) -> PipelineResult:
        for stage in self.stages:
            result = stage.execute(context)
            if not result.success:
                return PipelineResult(failed_at=stage.name, error=result.errors)
            context = context.with_update(stage.name, result.data)
        return PipelineResult(success=True, context=context)

# orchestration/agent_loop.py — 循环编排：复用 Stage，不重写业务逻辑
class AgentLoop:
    def __init__(self, pipeline: LinearPipeline, gate: Stage,
                 discovery: Stage, learn: Stage, review: Stage, policy: PolicyConfig):
        self.pipeline = pipeline  # 组合，不继承
        self.gate = gate
```

### 错误处理规范（异常 + Result 双轨）

不可恢复错误使用异常，可恢复错误使用 `Result[T, E]` 类型：

```python
# domain/result.py — 可恢复错误的显式表达
@dataclass(frozen=True)
class Ok(Generic[T]):
    value: T

@dataclass(frozen=True)
class Err(Generic[E]):
    error: E

Result = Ok[T] | Err[E]

# 异常 vs Result 的边界
# | 场景                   | 处理方式                                |
# |------------------------|----------------------------------------|
# | gate_fail              | Result[GateDecision, GateFailure]      |
# | channel_error          | Result[DeliveryResult, ChannelFailure] |
# | discovery_empty        | Result[list[Candidate], DiscoveryEmpty]|
# | FabricationGuardError  | 异常 — 不可恢复，终止                    |
# | EvidenceValidationError| 异常 — 不可恢复，终止                    |
# | PolicyError            | 异常 — 配置错误，终止                    |

# errors/exceptions.py — 仅保留不可恢复异常
class PiProofError(Exception):
    """所有不可恢复业务异常的基类"""
    category: ErrorCategory
    recoverable: bool = False

class EvidenceValidationError(PiProofError):
    """证据不合规（缺 results/artifacts）"""
    category = ErrorCategory.EVIDENCE

class FabricationGuardError(PiProofError):
    """生成阶段检测到无证据内容"""
    category = ErrorCategory.GENERATION

class PolicyError(PiProofError):
    """配置错误"""
    category = ErrorCategory.POLICY
```

### 应用资产与本地职业资料边界（2026-11-21）

### 历史已审官源岗位的离线质量复核

- 独立显式内部入口只读接受仍可核对的已审官源目标；要求原始画像、线索、来源身份与完整正文指纹双向一致。当前已审核的必备项和加分项必须分别可唯一定位到对应明确章节的完整原文条款；不信任概括条款、不将加分项升级，不用伪造未审记录打通入口。
- 复用当前职业与证据池审核、来源快照、方向规则、逐要求评审与定向片段验证。单次最多四次本机 Splash 请求（包含修复），临时缓存自动清理；成果证据不足则不给片段。已审并不代表来源全部重验或符合现时招聘状态；企业岗位的展示路径编号不会被推断成平台岗位编号。
- 结果仅作内部质量复核，永远不可交付、批准或发出；不改原岗位、批准记录、用户简历、证据或投递数据，不生成可供正式生成复用的审计/导出文件。现有底稿仅作人工对照。

### 已绑定引用文档的精确复验

普通证据编辑和保留同一材料、文档及完整材料标志的既有重审，可只重验已存文档引用。每条引用须唯一定位于冻结清单中受信任的文件，从当前文件全字节哈希核验后重建片段并比对文档 ID、原文与哈希；缓存不是证据。所选文件变更、缺失、引用歧义、路径不合法或任何冲突均阻断。新增绑定、整份材料、浏览、导入与刷新仍走原整份清单契约。保留审批复位与重审规则；匹配/预览用当前捕获的实际来源文件哈希，不降低资格或输出门槛。
旧卡缺少材料指纹时保留未重验口径；不以部署补丁静默更新入池资格。精确重审成功可保存既有材料指纹，随后实际消费会捕获对应原文件、材料清单、元信息与缓存的指纹；既有职业档案引用的来源绑定若因新增实际文件约束变化，仍按当前档案审查规则判断。
